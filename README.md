### 상태 관리

`Provider`와 `ChangeNotifier`를 사용했습니다.

관심 종목 상태를 `WatchlistProvider`에서 관리하여
관심 종목 화면, 검색 화면, 상세 화면에서 동일한 상태를
공유하도록 구성했습니다.

이를 통해 검색 화면에서 관심 종목을 등록하거나
상세 화면에서 관심 종목을 해제한 경우에도
다른 화면의 즐겨찾기 상태가 즉시 반영되도록 했습니다.

### 차트

별도의 차트 패키지 대신 Flutter의 `CustomPainter`를 사용해
캔들 차트를 직접 구현했습니다.

캔들, 거래량, Area Fill, 가격 축, Crosshair 및 Tooltip을
하나의 차트에서 직접 제어할 수 있고,
과제에서 제공한 디자인 토큰의 색상을 세밀하게 적용하기 위해
CustomPainter 방식을 선택했습니다.

## 4. 직접 판단한 부분

### Toast 노출 시간

관심 종목 등록/삭제 시 Toast를 약 2초간 노출하고
자동으로 사라지도록 구현했습니다.

사용자의 작업 결과를 인지할 수 있을 정도의 시간을 확보하면서도
화면을 계속 가리지 않도록 짧은 피드백으로 판단했습니다.

연속으로 발생하는 Toast는 여러 개를 쌓지 않고
현재 메시지를 교체하도록 처리했습니다.

### 시세를 받지 못한 종목의 정렬

현재가순과 등락률순 정렬에서는 아직 시세를 받지 못한 종목을
항상 목록의 하단에 배치했습니다.

미수신 상태를 0으로 간주하면 실제 0원/0%인 데이터와
구분할 수 없고 정렬 결과가 왜곡될 수 있기 때문에
로딩 상태를 별도로 판단하도록 구현했습니다.

가나다순에서는 시세 수신 여부와 관계없이 종목명 기준으로 정렬했습니다.

## 막혔던 지점과 해결 방법

### 1. Flutter/Dart 환경에 익숙하지 않았던 점

Flutter와 Dart를 처음 사용하는 환경이라 기존에 익숙했던 React/JavaScript와 다른 위젯 구조와 상태 관리 방식에 적응하는 데 시간이 필요했습니다.

특히 `StatelessWidget`, `StatefulWidget`, `BuildContext`, `ChangeNotifier`, `Provider` 등의 개념과 Flutter의 위젯 트리를 이해하면서 구현을 진행했습니다.

처음부터 모든 코드를 한 번에 작성하기보다 작은 화면 단위로 구현한 뒤 에뮬레이터에서 직접 실행하며 UI와 동작을 확인했습니다. 이후 필요한 기능을 하나씩 추가하는 방식으로 진행하여 Flutter 구조에 적응했습니다.

---

### 2. 네이버 금융 API 응답 구조를 파악하는 과정

관심 종목과 상세 화면의 실시간 시세를 구현하기 위해 네이버 금융의 실시간 시세 데이터를 사용했습니다.

처음에는 API 응답에서 어떤 필드가 종목 코드, 현재가, 전일 종가 등에 해당하는지 바로 알기 어려웠습니다.

실제 API 응답을 직접 확인하면서 필요한 필드를 하나씩 매핑했습니다.

- `cd` → 종목 코드
- `nv` → 현재가
- `pcv` → 전일 종가
- `ov` → 시가
- `hv` → 고가
- `lv` → 저가
- `aq` → 누적 거래량
- `countOfListedStock` → 상장 주식 수

이후 API 응답을 화면에서 직접 사용하는 대신 DTO로 변환하도록 구성하여 UI에서는 의미가 명확한 필드를 사용할 수 있도록 했습니다.

---

### 3. 일봉 데이터의 EUC-KR 인코딩 문제

상세 화면의 일봉 데이터는 네이버 금융의 HTML 페이지를 파싱하여 사용했습니다.

이 과정에서 응답 데이터가 UTF-8이 아닌 EUC-KR로 제공되어 한글 데이터가 정상적으로 처리되지 않는 문제가 있었습니다.

응답의 `bodyBytes`를 그대로 사용하고 `charset_converter`를 이용하여 EUC-KR에서 UTF-8 문자열로 변환한 뒤 HTML parser에 전달하는 방식으로 해결했습니다.

이를 통해 종목의 일별 시세 데이터를 정상적으로 파싱할 수 있었습니다.

---

### 4. HTML 형태의 일봉 데이터를 파싱하는 과정

일봉 데이터가 JSON 형태가 아니라 HTML 테이블 형태로 제공되기 때문에 필요한 데이터를 직접 찾아야 했습니다.

HTML의 `table.type2 tr`을 기준으로 행을 탐색하고 각 행의 `td` 데이터를 확인하여 날짜, 종가, 시가, 고가, 저가, 거래량을 추출했습니다.

또한 헤더나 불필요한 행이 데이터 목록에 포함되지 않도록 날짜 형식을 정규식으로 검사했습니다.

파싱한 데이터는 별도의 `DailyPriceDto`로 변환하여 화면에서는 파싱 로직과 분리된 형태로 사용할 수 있도록 했습니다.

---

### 5. 기간별 차트 데이터를 구성하는 과정

상세 화면에서 `1개월 / 3개월 / 6개월 / 1년`을 모두 지원해야 했기 때문에 선택된 기간에 따라 필요한 일봉 데이터의 개수가 달라졌습니다.

각 기간에 필요한 데이터 수를 기준으로 API 페이지를 추가 요청하고 데이터를 합친 뒤 차트와 일별 테이블에 전달하는 방식으로 구현했습니다.

- 1개월 → 약 25개
- 3개월 → 약 70개
- 6개월 → 약 130개
- 1년 → 약 260개

이를 통해 단순히 탭의 텍스트만 변경하는 것이 아니라 선택한 기간에 맞춰 실제 차트와 일별 데이터가 변경되도록 구현했습니다.

---

### 6. 캔들 차트를 직접 구현하는 과정

캔들 차트는 별도의 차트 패키지를 사용하지 않고 Flutter의 `CustomPainter`를 이용해 직접 구현했습니다.

처음에는 화면 좌표와 실제 가격 데이터를 어떻게 연결할지 고민이 필요했습니다.

가격의 최고값과 최저값을 기준으로 차트 영역을 정규화하고 각 데이터의 시가, 고가, 저가, 종가를 화면의 Y 좌표로 변환하여 몸통과 꼬리를 그리는 방식으로 구현했습니다.

추가 기능으로 거래량 바, 종가 영역 채우기, 가격 축 라벨, 크로스헤어와 툴팁까지 같은 `CustomPainter`에서 처리했습니다.

직접 그리는 방식을 선택하면서 과제에서 제공한 디자인 토큰을 차트에 세밀하게 적용할 수 있었습니다.

---

### 7. 관심 종목 상태를 여러 화면에서 동기화하는 과정

관심 종목 기능이 관심 화면뿐만 아니라 검색 화면과 상세 화면에서도 사용되기 때문에 각 화면에서 별도의 관심 상태를 관리하면 상태가 서로 달라질 수 있는 문제가 있었습니다.

이를 해결하기 위해 `Provider`와 `ChangeNotifier`를 이용하여 `WatchlistProvider`에서 관심 종목 상태를 하나로 관리했습니다.

관심 종목 추가/삭제가 발생하면 Provider가 상태를 변경하고 `notifyListeners()`를 호출하도록 구성했습니다.

그 결과 다음과 같은 상태가 동일하게 유지되도록 했습니다.

- 검색 화면에서 관심 종목 추가 → 관심 종목 화면에 즉시 반영
- 검색 화면에서 관심 종목 삭제 → 관심 아이콘 즉시 반영
- 상세 화면에서 관심 종목 해제 → 뒤로 이동했을 때 관심 목록에서 제거
- 각 화면의 별 아이콘 → 동일한 관심 상태를 표시

---

### 8. 앱을 재실행했을 때 관심 종목과 정렬 기준이 사라지는 문제

관심 종목과 정렬 기준은 앱을 종료하면 초기화되는 상태가 아니라 다시 실행해도 유지되는 것이 더 자연스럽다고 판단했습니다.

이를 위해 `shared_preferences`를 사용하여 관심 종목의 코드, 이름, 시장 정보를 저장하고 정렬 기준도 함께 저장했습니다.

앱 실행 시 저장된 값을 복원한 뒤 관심 종목의 실시간 시세를 다시 조회하도록 구성했습니다.

관심 종목 자체와 실시간 시세 데이터를 분리하여 저장함으로써 앱을 재실행해도 저장된 종목은 유지하면서 최신 시세를 다시 받을 수 있도록 했습니다.

---

### 9. 시세를 아직 받지 못한 종목의 정렬 문제

실시간 시세를 가져오는 동안에는 일부 종목의 현재가와 등락률을 알 수 없는 상태가 발생할 수 있었습니다.

이때 시세를 받지 못한 종목을 단순히 `0`으로 취급하여 정렬하면 실제 가격이 낮은 종목처럼 잘못 배치될 수 있다고 판단했습니다.

따라서 `현재가순`과 `등락률순`에서는 시세를 아직 받지 못한 종목을 항상 목록의 아래쪽에 배치하고, 시세를 받은 종목끼리만 실제 값으로 정렬하도록 구현했습니다.

반면 `가나다순`에서는 시세 수신 여부와 관계없이 종목명을 기준으로 정렬하도록 처리했습니다.

---

### 10. 검색 요청이 너무 자주 발생하는 문제

검색창에 문자를 입력할 때마다 API를 요청하면 입력 중 불필요한 네트워크 요청이 반복될 수 있습니다.

이를 방지하기 위해 약 300ms의 debounce를 적용했습니다.

사용자가 입력을 멈춘 뒤 검색 요청을 보내도록 하여 불필요한 API 호출을 줄였고, 검색 요청 중에는 로딩 상태를 표시하도록 구성했습니다.

---

### 11. 긴 검색어와 긴 종목명으로 인한 레이아웃 문제

검색어가 지나치게 길거나 종목명이 화면에서 표시할 수 있는 영역보다 길어지는 경우 UI가 깨지지 않도록 처리할 필요가 있었습니다.

긴 검색어의 경우 결과가 없을 때 검색어를 한 줄로 제한하고 `ellipsis`를 적용하여 화면 영역을 벗어나지 않도록 했습니다.

종목명과 같은 텍스트 영역에도 필요한 경우 `maxLines`와 `overflow`를 적용하여 작은 화면에서도 레이아웃이 깨지지 않도록 처리했습니다.

---

### 12. 네트워크 요청 중 로딩 상태를 표현하는 과정

API 요청이 완료되기 전에 빈 화면을 보여주면 사용자가 데이터가 없는 것인지 아직 불러오는 중인지 구분하기 어렵습니다.

이를 해결하기 위해 초기 데이터 로딩 시 스켈레톤 UI를 표시하고, 검색 화면에서는 검색 요청 중 로딩 상태를 표시했습니다.

관심 종목 화면에서도 아직 실시간 시세를 받지 못한 행은 스켈레톤 형태로 표시하여 데이터 로딩 상태를 사용자가 인지할 수 있도록 했습니다.

---

### 13. 일별 데이터 무한 스크롤 구현

상세 화면의 일별 데이터는 한 번에 모든 데이터를 불러오는 대신 필요한 데이터를 먼저 표시하고 스크롤이 하단에 가까워지면 다음 페이지를 요청하도록 구현했습니다.

페이지가 추가될 때 기존 데이터와 연결되는 등락률도 다시 계산해야 했습니다.

특히 이전 페이지의 마지막 데이터는 다음 페이지의 첫 번째 데이터가 추가되어야 정확한 전일 대비 등락을 계산할 수 있기 때문에 새 데이터를 추가할 때 기존 마지막 행의 변화량도 함께 갱신하도록 처리했습니다.

---

### 14. 최근 검색어 저장과 중복 처리

최근 검색어는 단순히 화면에만 저장하지 않고 앱을 다시 실행해도 유지되도록 `shared_preferences`에 저장했습니다.

동일한 검색어를 다시 검색한 경우 중복으로 쌓이지 않도록 기존 검색어를 제거한 뒤 가장 최근 검색어를 맨 앞에 추가하는 방식으로 처리했습니다.

또한 최근 검색어가 지나치게 많아지지 않도록 최대 10개까지만 저장하도록 제한했습니다.

---

### 15. Flutter 위젯 테스트에서 화면 제목을 찾지 못했던 문제

기존 테스트에서는 `MaterialApp`의 `title`에 지정한 문자열을 실제 화면에 표시되는 텍스트로 잘못 판단하여 해당 텍스트를 찾는 방식으로 테스트하고 있었습니다.

하지만 `MaterialApp.title`은 앱의 메타데이터이며 화면에 `Text` 위젯으로 렌더링되는 값이 아니기 때문에 테스트에서 해당 문자열을 찾을 수 없었습니다.

따라서 실제 화면에 존재하는 위젯을 기준으로 테스트하도록 변경하고, 현재 앱의 다크 테마가 정상적으로 적용되었는지를 확인하는 방식으로 테스트를 수정했습니다.
